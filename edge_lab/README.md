# Edge Lab — โรงงานวิจัยหา edge บน Binance Futures

ไม่ใช่บอทเทรด เป็นเครื่องมือตอบคำถามว่า **"ไอเดียนี้มี edge จริงไหม"** ให้จบภายในวันเดียว

## คำถาม 6 ข้อที่ตั้งไว้ให้

ทุกข้อเลือกมาด้วยเกณฑ์เดียว: **ต้องตอบได้ว่าใครถูกบังคับให้เทรด และทำไม** ไม่ใช่ "กราฟรูปนี้สวยดี"

### H1 — เมื่อ funding สุดขั้ว ฝั่งที่แออัดถูกบีบจนต้องปิดหรือเปล่า

> ในเหรียญที่ funding z-score เกิน ±2 (เทียบ 30 วันย้อนหลัง) ราคาช่วง 8 ชั่วโมงหลัง settlement เคลื่อนสวนทางกับฝั่งที่แออัดกี่ bps

**กลไก** — funding บวกสูง = long จ่ายเงินให้ short ทุก 8 ชม. ตำแหน่งที่เสียเงินตลอดเวลาคือตำแหน่งที่มีนาฬิกาจับเวลาอยู่
**Null** — ไม่มีความสัมพันธ์
**ข้อมูล** — มีย้อนหลังเต็ม ✅

### H2 — carry factor ในคริปโตให้ผลตอบแทนเกินค่าธรรมเนียมไหม

> long เหรียญที่ funding ติดลบสุด 20% / short ที่บวกสุด 20% รีบาลานซ์ทุก 8 ชม. หลังหัก turnover cost เหลือเท่าไหร่

**กลไก** — คนที่ยอมจ่าย funding แพงคือคนที่ต้องการ leverage ทันทีโดยไม่สนราคา นั่นคือค่าเช่าที่เราเก็บได้
**จุดตาย** — turnover สูงมาก ต้นทุนกินก่อน นี่คือข้อที่ผมคาดว่าจะไม่ผ่าน แต่ต้องวัดถึงจะรู้
**ข้อมูล** — มีย้อนหลังเต็ม ✅

### H3 — ตลาดช่วงเอเชียตอบสนองต่อคืนอเมริกายังไง

> วันที่ US session (UTC 13-21) เคลื่อนเกิน 1.5% ช่วง 07:00-15:00 ICT วันถัดไปสานต่อหรือย้อนกลับ

**กลไก** — คนไทย/เอเชียตื่นมาเห็นข่าวที่เกิดตอนนอน แล้วตอบสนองพร้อมกันในหน้าต่างเวลาแคบ
**ทำไมน่าสนใจสำหรับคุณโดยเฉพาะ** — งานวิจัยคริปโตเกือบทั้งหมดเขียนจากฝั่งตะวันตก ช่วงเวลานี้ถูกศึกษาน้อยกว่ามาก และคุณอยู่ในนั้น
**ข้อมูล** — klines อย่างเดียว ✅

### H4 — perp ที่เพิ่ง list มี inventory effect ไหม

> 14 วันแรกหลัง perp เปิดเทรด ผลตอบแทนส่วนเกินเทียบ BTC เป็นเท่าไหร่

**กลไก** — market maker ต้องสร้าง inventory จากศูนย์ ไม่มีประวัติราคาให้อ้างอิง spread กว้างผิดปกติ และมี hype flow ทางเดียว
**ข้อมูล** — `onboardDate` จาก exchangeInfo + klines ✅

### H5 — สุดสัปดาห์ราคาเหวี่ยงเกินจริงเพราะไม่มีใครรับหรือเปล่า

> เสาร์-อาทิตย์ที่เคลื่อนเกิน 2% วันจันทร์ย้อนกลับกี่ bps

**กลไก** — liquidity หายไปครึ่งหนึ่ง สถาบันปิดเครื่อง แต่ข่าวไม่หยุด → order เดียวกันดันราคาได้ไกลกว่าปกติ แล้วจันทร์ของกลับเข้าที่
**ข้อจำกัด** — n น้อย (52 ครั้ง/ปี) ต้องใช้ข้อมูลหลายปีถึงจะสรุปได้
**ข้อมูล** — klines อย่างเดียว ✅

### H6 — perp premium เหนือ spot กลับด้วยราคา หรือกลับด้วย funding

> เมื่อ basis z-score เกิน ±2.5 ราคา perp ใน 24 ชม.ถัดไปเคลื่อนไปทางไหน

**กลไก** — arbitrageur บีบ basis ให้กลับเสมอ แต่คำถามคือใครเป็นฝ่ายปรับ ถ้าเป็นราคา = เทรดได้ ถ้าเป็น funding = เทรดไม่ได้
**นี่คือคำถามที่ผมคิดว่าน่าสนใจที่สุดในหกข้อ** เพราะคำตอบมีค่าไม่ว่าจะออกทางไหน
**ข้อมูล** — perp klines + spot klines ✅

## เกณฑ์ที่ตั้งไว้ (ตั้งก่อนเห็นผล — ห้ามขยับทีหลัง)

| ข้อ | เกณฑ์ | เหตุผล |
|---|---|---|
| ต้นทุน | หัก 11 bps ไป-กลับทุกไม้ | taker 0.045%×2 + slippage 1bp×2 |
| ตัวเลขที่นับ | **OOS เท่านั้น** (30% ท้าย) | IS ใช้ดูว่าโค้ดไม่พัง เท่านั้น |
| CI | ขอบล่าง bootstrap ต้อง > 0 | ค่าเฉลี่ยบวกอย่างเดียวไม่พอ |
| t-stat | \|t\| > 3.0 | เข้มกว่า 1.96 เพราะทดสอบ 6 ข้อพร้อมกัน |
| n | ≥ 100 ไม้ | ต่ำกว่านี้ไม่มีสิทธิ์เรียกว่าผ่าน |
| Sharpe | > 0.5 | หลังหักต้นทุนแล้ว |

CI ใช้ **moving-block bootstrap** ไม่ใช่ t-test ธรรมดา เพราะ return มัน autocorrelate — t-test ปกติจะให้ CI แคบเกินจริงแล้วทำให้เราเชื่อผิด

## ผลตรวจสอบเครื่องมือ

รันบนข้อมูลสังเคราะห์ที่รู้คำตอบล่วงหน้า:

| edge ที่ฝังไว้ | ที่เครื่องมือวัดได้ | ผ่านเกณฑ์ไหม |
|---|---|---|
| 0 bps (random walk ล้วน) | ไม่เจอ | ✗ ถูกต้อง — ไม่มี false positive |
| 60 bps | 59.5 bps | ✗ t=1.73 ยังไม่พอ |
| 100 bps | 95.6 bps | ✗ t=2.77 เฉียด |
| 150 bps | 140.9 bps | ✓ t=4.05 |

สองอย่างที่อ่านได้จากตารางนี้:

1. **วัดขนาด edge ได้แม่น** (59.5 จาก 60, 140.9 จาก 150) ไม่มี lookahead leak
2. **ที่ n≈790 เครื่องมือจับ edge ต่ำกว่า ~120 bps ไม่ได้** — ไม่ใช่เพราะบั๊ก แต่เพราะ noise 8 ชม. อยู่แถว 340 bps ถ้าอยากจับ edge เล็กกว่านี้ต้องเพิ่มจำนวนเหรียญหรือย้อนข้อมูลไกลขึ้น

ข้อ 2 สำคัญ: **ถ้ารันจริงแล้วไม่มีข้อไหนผ่าน อย่าเพิ่งสรุปว่าไม่มี edge** ให้สรุปว่า "ไม่มี edge ที่ใหญ่พอให้เห็นด้วยข้อมูลเท่านี้" แล้วเพิ่มข้อมูล

## เพิ่มสมมติฐานของคุณเอง

เขียนฟังก์ชันที่คืน `pd.Series` ของ gross return ต่อไม้ แล้วลงทะเบียนใน `REGISTRY` ของ `hypotheses.py` — stats engine จัดการที่เหลือให้

กฎสามข้อที่ห้ามละเมิด:

```python
z = (s - s.rolling(w).mean().shift(1)) / s.rolling(w).std().shift(1)   # shift(1) เสมอ
fwd = close.shift(-h) / close - 1                                       # อนาคตอยู่ฝั่ง -h
# อย่า normalize ด้วย mean/std ของทั้ง dataset
```

ทุกครั้งที่เพิ่มข้อใหม่ ให้รัน `--synthetic` ก่อน ถ้าข้อใหม่ "ผ่าน" บนข้อมูลสุ่ม แปลว่ามี leak
